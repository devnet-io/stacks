# Current architecture

This document describes implemented behavior in this checkout. Hosted direction belongs in [RFCs](rfcs/README.md).

No compatibility milestone has been declared. Unused command and adapter surfaces may therefore be removed instead of retained as legacy workflow. Durable definitions, bindings, and events remain protected: incompatible stored data must be migrated explicitly or rejected with a clear error, never silently rewritten, corrupted, or discarded.

## Repository shape

The npm workspace contains a TypeScript core, CLI, stdio MCP adapter, loopback HTTP adapter, repository-agent-instruction adapter, and React local UI. `apps/cloud` is only a reserved future boundary.

```text
src/core/          domain, catalog, filesystem, Git, context, and events
src/application/   StacksApplication use cases and versioned adapter-neutral responses
src/http/          loopback local API
src/ui/            UI launcher
src/cli.ts         human and automation CLI
src/mcp/           global stdio MCP adapter
src/agent/         bounded repository instruction adapters
apps/web/          local management and documentation UI
apps/cloud/        placeholder only
```

## Global catalog

New Stacks are registered by immutable ID and readable `namespace/name`. The catalog stores readable Stack definitions and machine-local component path bindings in the platform config directory, and append-only events, locks, and other operational state in the platform state directory.

Definitions and bindings are ordinary JSON. SQLite and hosted storage are not canonical. Linux uses XDG config/state conventions; macOS and Windows use native application-data locations, always with lowercase `stacks`.

A registered definition does not imply a Stack workspace directory. Every component has an explicit local binding. A Git URL describes source provenance while its binding describes where that repository lives on this machine. Multiple Stacks may bind the same directory. Stacks writes no membership marker into a component repository.

The `workspace`, relative `path` source, `stacks init`, and `--root` surfaces remain implemented for the repository's older examples and migration compatibility.

## Component and context model

Components are ordinary graph nodes. Software, standards, design systems, infrastructure references, and documentation may all be components; `kind` describes intent but does not create a second storage hierarchy. Components provide capabilities, consume capabilities, depend on other components, and export bounded context resources.

Within one immutable Stack identity, `component.id` is the stable logical reference used by bindings, relationships, requests, events, and work. It is user-chosen at creation and immutable afterward. Display name, description, kind, and declared access are editable portable metadata; local path changes use the separate binding operation. Access is advisory context for agents and people, not operating-system permission enforcement. Capability requirements are required by default and may be marked optional. Missing required providers are context errors, while missing optional providers are warnings; both remain explicit in graph output. Direct `dependsOn` edges are currently required.

An explicitly bound component may optionally publish a strict `.stack/component.json` version `0.1` descriptor containing only capability exports, their bounded context paths, and optional portable artifact identities. Stacks safely reads that fixed file as untrusted provider-owned input: the descriptor is size/count bounded, unknown fields and duplicate capabilities are rejected, lexical escapes and descriptor symlink escapes are refused, and context materialization still applies canonical-root and byte-budget checks. Consumer requirements remain Stack-owned. Descriptor exports form a base layer; an explicit Stack export for the same capability replaces the complete descriptor entry, including artifact metadata. Invalid or unavailable descriptors contribute nothing and appear in component, status, validation, context-warning, CLI, MCP, HTTP, and Manage UI diagnostics.

An artifact identity contains an extensible ecosystem, artifact name, and optional component-relative artifact root. Component and Graph views expose these declarations. For an npm artifact attached to a consumed capability, context resolution derives a machine-local `file:` candidate from explicit provider and consumer bindings. It also tells the agent to preserve existing project configuration, use an existing workspace convention when applicable, and prefer an established registry before considering that fallback. Stacks does not inspect every workspace topology, edit package manifests, invoke package managers, run lifecycle scripts, or publish packages. npm, pnpm, Yarn, and Bun interpret local packages differently, so the repository's own tooling remains authoritative.

Directory membership is derived from explicit machine bindings. A queried path directly matches a component when it is the bound root or lies beneath it. If there are no direct matches, discovery returns bound components beneath the queried ancestor as lower-confidence `ancestor` results. Direct matches suppress unrelated descendant matches, and neither mode guesses when multiple Stacks or components qualify. Discovery never relies on repository names or ownership markers. New components persist the neutral `component` kind when no optional kind is supplied, while capabilities remain the functional contract.

Repository activation is opt-in. `stacks agent install` manages only a uniquely marked block inside a regular, non-symlinked `AGENTS.md`, preserves all other content and line endings, writes atomically, and refuses malformed markers. The managed instructions perform membership discovery at runtime instead of embedding a Stack identity. Print and check are read-only; remove deletes only the managed block.

Context resolution is deterministic and provenance-rich. Registered Stacks can upsert capability exports with one bounded context path, consumer requirements with an optional explicit provider, and component-relative guidance through the shared CLI, MCP, HTTP, and Manage adapters. Resolution verifies declared paths against the owning component root and reports missing or ambiguous providers. Materialization canonicalizes each file again, rejects symlink escapes, directories, binary content, and unreadable paths, then returns bounded text with provenance, content hashes, truncations, and explicit omissions.

Task terms rank declared path, description, tag, reason, and capability metadata within each guidance strength; declared priority and deterministic ties follow. Standalone context resolution defaults to a 32 KiB orientation. The first turn in a session receives the same orientation cadence, while subsequent turns use an 8 KiB refresh; callers may set a hard positive byte budget up to 256 KiB. The returned briefing has a stable digest, and `turn.started` records that digest plus mode/budget/count metadata without persisting task text or file contents. Resolved context also carries at most 20 non-terminal capability requests where the target is requester or expected provider. Refresh currently means a smaller current-plan materialization rather than a change-aware delta. Model-specific token enforcement, removal, and multi-path editing remain unfinished.

## Adapters

- CLI, MCP, and HTTP handlers call one `StacksApplication` interface. `LocalStacksApplication` is the implemented in-process adapter over the catalog, filesystem, Git, context, and event modules. No local daemon is required.
- Application reads compose declared Stack data with valid provider descriptors into an effective graph while retaining the raw declared manifest and descriptor provenance. Descriptor files are never copied into or written by the machine catalog.
- `stacks status` without a selector inspects every registered Stack. Commands that require one Stack select it with `--stack namespace/name`; the current directory is never an implicit Stack. Compatibility manifests require explicit `--root` (or the explicitly legacy `init` command).
- `stacks ui` starts one Node loopback server that serves both the packaged static Vite application and `/api/v0.1/*`. It prefers port 3210, selects the next free port when necessary, and needs no API-origin query parameter or separate web runtime. The UI calls `/api/v0.1/stacks`, then supplies a Stack selector above the sidebar navigation to Overview, Graph, Activity, Requests, Manage, Tools & agents, and Documentation. The bottom application menu exposes the root package version and reserves a stable location for later account/settings surfaces.
- `stacks mcp` is one machine-catalog stdio adapter. It supplies standard initialization instructions, agent-readable instruction/CLI/MCP resources, and tools for discovery, component/context configuration, resolution, logical-work/turn inspection, and lifecycle reporting. Stack-specific MCP tools require `stack`; there is no local MCP port. A canonical MCP catalog is checked against the source transport and the packed installed transport. Agent clients own their loaded tool registries, so registration and MCP-contract upgrades require a client restart.
- Directory-scoped HTTP/UI and CLI behavior is retained only when an explicit legacy `--root` is supplied.

An HTTP implementation of `StacksApplication`, global CLI endpoint selection, and Streamable HTTP MCP are accepted direction in ADR 0007 but are not implemented. The intended remote service shares one origin and authentication boundary for the web UI, REST application API, and MCP. Local CLI and stdio MCP remain the defaults.

The loopback API exposes read-only Overview, Graph, Activity, logical-work detail, turn detail, capability-request list/detail, Integrations, component, catalog, and health routes plus JSON-only mutations for Stack creation, component addition/rebinding, capability exports/requirements, guidance, and capability-request creation/transitions. Browser mutations reject non-loopback origins. Catalog writers acquire a cross-process lock; new Stack files are committed before the catalog entry, and new component bindings are committed before the component definition, so lock-free readers do not observe partial reachable state. Overview reports live status, Graph renders the declarative provider/dependency relationships, and Activity separates logical work from Stack changes. Work rows retain their opening title and completion result, count child turns, and deep-link to work and turn detail pages with briefing, usage, path, and status evidence. Requests exposes list/create/detail/transition views with role-checked state changes and evidence; Manage exposes catalog/context mutations, and Tools & agents presents MCP plus repository activation. Documentation auto-discovers every repository Markdown file under `docs/`, reads navigation and lifecycle metadata from `docs/catalog.json`, exposes non-current warnings, nested heading navigation, and stable `view`, `document`, and `heading` query-parameter deep links, and intercepts repository-relative document links without maintaining a second prose copy. `npm run docs:check` requires every Markdown file to have unique lifecycle metadata and rejects missing files or broken relative Markdown links.

The root npm package version is the shared product version for CLI output, UI display, health responses, and integration metadata. Running UI processes register PID/origin/version plus a random control token under the platform state directory. `install:local` uses the authenticated loopback shutdown endpoint to retire registered processes before replacing the standalone installation. Version-aware UI reuse prevents a newly installed CLI from attaching to an older healthy server.

## Temporary installation test

The installation test exercises the complete local workflow against a clean temporary installation rather than the source CLI. It creates three explicitly bound component directories, preserves product-owned instructions while activating `AGENTS.md`, installs and imports a real local npm package with lifecycle scripts disabled, and drives one live stdio MCP connection through membership discovery, orientation and refresh turns, authoritative capability reuse, a cross-component request, separate provider work and completion, consumer verification, resumed work, and completed activity projections. The temporary Stack and installation are removed afterward. This is a deterministic protocol acceptance client, not an autonomous agent runner.

## Events and safety

Registered Stack creation, component addition, changed component bindings/configuration, capability-request creation/transitions, work starts, turn starts, turn completions, work completion, and usage are append-only JSONL events under a registered Stack's state directory. Capability requests have stable `requestId` identity, originate from active requester work, enforce provider/requester transition roles, and distinguish `provider-complete` from `consumer-verified`; they record coordination but never assign or schedule work. A `sessionId` identifies one logical work item, not a Codex chat or an individual response. Logical work may span clarifications, retries, and multiple turns; one chat may contain multiple work items. A work item permits one open turn; `turn_start` returns its context plan and bounded briefing, `turn_complete` requires the same `turnId`, and work completion refuses an open turn. Known live telemetry supplied with completion is appended as a linked usage event under the same writer lock and sync; delayed telemetry uses an explicit import operation. Older events without `turnId` remain readable and are never backfilled. Management events are appended by the shared application boundary after the catalog mutation commits; adapter provenance identifies CLI, web, or MCP, and configuration upserts preserve history instead of rewriting prior events. Independent processes serialize appends through a per-Stack exclusive lock; readers never acquire the writer lock. A lock timeout fails with its exact path instead of deleting a possibly live lock. Monetary values require `reported`, `estimated`, or `allocated` provenance. Read commands never mutate component repositories. Git sync may clone to an explicit path or fetch with `--update`, but never resets, cleans, merges, rebases, overwrites dirty work, or silently moves a repository.
